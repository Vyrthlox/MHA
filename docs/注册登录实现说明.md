# 注册 / 登录 实现说明

> 适用版本：后端 `code/ai-springboot`（Spring Boot 4.1.1）· 前端 `ai-vue`（Vue 3.5 + Vite 8）
> 最后更新：2026-10-16（本次新增 §5.8 注册邮箱验证码、§6.7 前端发送按钮）
> 首次建立：2026-10-13

本文记录注册、登录、JWT 鉴权、路由守卫这条主链路的**实现逻辑与落地细节**，重点写清楚
「为什么这么做」以及**踩过的坑**——后者比代码本身更容易在后续维护中被重新踩一遍。

---

## 1. 范围

打通链路：**发送邮箱验证码 → 注册 → 登录 → 携带 token 访问受保护接口 → 前端路由守卫 → 退出登录**。

不在范围内（本期未做）：
- 刷新 token / 主动续期（当前是到期即重新登录）
- 忘记密码、改密（邮箱验证码目前**只服务注册**，见 §5.8.6）
- 管理员权限的接口级鉴权（`status` 已解析并下发，但尚无接口按它做拦截）
- Redis 存 token 黑名单（当前完全无状态，退出登录只是前端清 localStorage）

## 2. 整体链路

```
浏览器 (5173)
  │
  │  axios (baseURL=/api)  →  请求拦截器塞 Authorization: Bearer <token>
  ▼
Vite dev server  ──  proxy /api → http://localhost:8080（不 rewrite）
  ▼
Tomcat (context-path=/api)
  │
  ├─ 白名单(/user/login、/user/register、/user/email-code …) ──► UserController
  │
  └─ JwtAuthInterceptor.preHandle
        ├─ 无 / 坏 token → throw BusinessException(-1)
        └─ 通过 → UserContext.set(LoginUser)  ──────────► UserController
                                                              │
                                                              ├──────────────┐
                                                              ▼              ▼
                                 UserService（@Transactional）        EmailCodeService
                                                              │              │
                                        ┌─────────────────────┴───┐          │
                                        ▼                         ▼          ▼
                                  sys_users                 sys_user_auths   Redis
                                  (状态/锁定)                (用户名/邮箱/密码) (验证码/冷却/失败计数)
                                                                              │
                                                                              ▼
                                                              MailDelivery → SMTP 或 日志
```

统一响应体 `{code, msg, data}` 全程不变，**HTTP 状态码恒为 200**（原因见 §5.3）。

注意邮箱验证码这条支路**不碰 MySQL**：`sys_users` / `sys_user_auths` 只在最终提交注册时写，
验证码本身全部活在 Redis 里（§5.8）。

## 3. 技术选型决策

| 决策点 | 选择 | 被否决的方案 / 原因 |
|---|---|---|
| 认证方式 | **JWT 无状态 token** | 未上 Spring Security 全套过滤器链——本项目的鉴权需求只有「有没有合法 token」，引入完整框架的收益抵不上它的复杂度和「默认锁死所有接口」的风险 |
| 密码哈希 | **BCrypt**（`spring-security-crypto`） | 只取这一个 jar。已验证依赖树里**只有** `spring-security-crypto:7.1.1`，**没有** `spring-security-web` / `-config` / `-core`，即过滤器链完全没有被引入 |
| 鉴权挂载点 | **`HandlerInterceptor`** | 不用 `OncePerRequestFilter`，理由见 §5.4（异常处理一致性，这是决定性的） |
| 持久层 | **Spring Data JDBC** | 项目既有的 `CrudRepository` 风格；非 JPA |
| JWT 库 | **jjwt 0.13.0** | 不在 Spring Boot BOM 中，必须显式写版本号 |
| 模型厂商 | **OpenAI 兼容接口** | 便于切 DeepSeek / 通义千问 / Kimi，只改 base-url 与 model |
| 验证码存储 | **Redis** | 不用 MySQL：TTL 与覆盖写恰好就是「5 分钟过期 + 重发作废旧码」这两个需求，见 §5.8.1 |
| 邮件发送 | **`spring-boot-starter-mail` + 双模式** | SMTP 未配置时降级为打日志，不阻塞开发与联调（§5.8.7） |

### 3.1 版本兼容性（重要）

- **Spring Boot 4.1.1 → Spring Framework 7.0.9**
- **Spring AI 必须用 2.0.x**。Spring AI 1.1.x 依赖 Spring Framework 6.2，与 Boot 4 的 7.0.9 **不兼容**。本项目用 `spring-ai-bom:2.0.1` 统一管理。
- **Jackson 2 / Jackson 3 并存**（已用 `dependency:tree` 核实）：

  | | 包名 | 版本 | 谁在用 |
  |---|---|---|---|
  | Jackson 3 | `tools.jackson.core` | 3.1.5 | Boot 4 的 Web MVC 序列化 |
  | Jackson 2 | `com.fasterxml.jackson.core` | 2.21.5 | `jjwt-jackson`、部分 Spring AI 组件 |

  两者包名不同，可以共存。**不要试图 exclude 掉其中一个来"解决"它**——那会打断另一方的运行期依赖。
  注意：手写 JSON 时要清楚自己用的是哪一个。

## 4. 数据库

### 4.1 两张表：主表 + 从表（已建立外键）

| 表 | 角色 | 职责 | 关键列 |
|---|---|---|---|
| `sys_users` | **主表** | 账号状态 | `id`、`status`、`locked_until`、`is_deleted`、`created_at`、`updated_at` |
| `sys_user_auths` | **从表** | 登录凭据 | `id`、`username`、`email`、`password_hash`、`salt`、`last_login_at`、`created_at`、`updated_at` |

`sys_user_auths.id` 与 `sys_users.id` 是**同一个值**，数据库层面已经建立了外键：

```sql
ALTER TABLE sys_user_auths
  ADD CONSTRAINT fk_sys_user_auths_user
  FOREIGN KEY (id) REFERENCES sys_users (id)
  ON DELETE CASCADE ON UPDATE RESTRICT;
```

落地时踩到一个**必须先处理的坑**：

- **两侧类型必须完全一致（含符号）**。`sys_users.id` 是 `BIGINT UNSIGNED`，
  而 `sys_user_auths.id` 原本是 `BIGINT`（有符号）。直接加外键会报
  **errno 3780（referencing/referenced column types incompatible）**。
  必须先把从表改成 `BIGINT UNSIGNED`：

  ```sql
  ALTER TABLE sys_user_auths MODIFY COLUMN id BIGINT UNSIGNED NOT NULL;
  ```

- **从表 `id` 不再是 `AUTO_INCREMENT`**。它的值必须由主表回填，让它自增等于放任数据库
  生成一个大概率不存在的 id（然后被外键拒绝）。去掉后，漏传 id 会直接报
  `Field 'id' doesn't have a default value`，错误更直白。

- **`ON DELETE CASCADE`**：删账号时凭据自动跟着删，物理上不可能留下孤儿凭据。
  **`ON UPDATE RESTRICT`**：主键本来就不会变，这条只是把意图写死。

外键是**兜底，不是事务的替代品**。`UserService.register` 仍然必须 `@Transactional`：
「先插主表拿自增 id、再插从表」这个顺序需要事务保护（从表失败要回滚主表）。
外键保证的是另一件事——**永远不会有指向不存在账号的凭据行**。

### 4.2 三个必须知道的坑

**坑 1：`sys_users.status` 的默认值曾经是 `1`，而 `1` = 管理员。**

线上表的默认值一直是 `2`，但 `docs/table.md` 里的 DDL 曾写成 `DEFAULT 1`。
两者不一致意味着：**照着文档重跑一次建表语句，每个新注册的人都会变成管理员。**
2026-10-18 已把文档统一为 `DEFAULT 2`，现在文档、DDL、线上表三者一致。

代码**仍然**显式写 `user.setStatus(STATUS_NORMAL_USER)`（`UserService`），不依赖列默认值：
默认值是 DBA 随时可以改的，而「新注册的人不能是管理员」是安全属性，不该押在它上面。
验证断言里也专门有一条 `status = 2`。

**坑 2：`created_at` / `updated_at` 由数据库维护，Java 侧必须标 `@ReadOnlyProperty`。**

这两列有 `DEFAULT CURRENT_TIMESTAMP` / `ON UPDATE CURRENT_TIMESTAMP`。若实体上不标
`@ReadOnlyProperty`，Spring Data JDBC 会**显式把 NULL 写进去**，MySQL 严格模式直接报
`Column 'created_at' cannot be null`。

**坑 3：`salt` 列 `NOT NULL`，但 BCrypt 并不使用它。**

BCrypt 把随机盐内嵌在哈希串里了。这里写固定占位符 `"bcrypt$embedded"` 而不是随机盐——
写随机盐会造成「这个盐真的参与运算」的误解。

### 4.3 `is_deleted` 的类型选择

用 `Integer`（0/1）而非 `Boolean`，并显式标 `@Column("is_deleted")`。

原因：Spring Data 的属性名归一化可能把 `is` 前缀剥掉，映射到一个**不存在的 `deleted` 列**。
显式写列名 + 用 `Integer` 两个措施一起上。

### 5.2 统一响应体

`Result<T>{code, msg, data}`，状态码常量在 `ResultCode`：

| 常量 | 值 | 含义 |
|---|---|---|
| `SUCCESS` | `200` | 成功 |
| `LOGIN_EXPIRED` | **`-1`** | 登录过期 / 未认证 —— **前端契约的一部分** |
| `ERROR` | `500` | 通用业务错误 |

> ⚠️ **`-1` 是跨端约定的哨兵值。** 前端 `request.js` 看到它就清 localStorage 并跳登录页。
> 改动它必须同步改前端。

**不要新增单参数的 `success(String msg)` 重载。** 在泛型下 `Result.success("注册成功")` 会绑定到
`success(T data)`，静默产出 `{"code":200,"msg":"操作成功","data":"注册成功"}`——消息跑到 data 里去了。
统一用两参数形式 `success(msg, data)`。

### 5.3 全局异常处理：为什么全部返回 HTTP 200

`GlobalExceptionHandler`（`@RestControllerAdvice`）**刻意让所有分支都返回 HTTP 200**，错误信息
放在响应体的 `code` 字段里。

原因：前端响应拦截器把 `code === -1` 的登录过期逻辑放在了**成功分支**里。若这里返回 HTTP 401，
axios 会走 error 分支，前端就**认不出**这个约定的哨兵值了。

代价：真实的服务端错误也是 HTTP 200 + `code:500`，所以**前端必须按 `code` 分支判断，不能按
HTTP 状态码**。前端为此在 axios 的 error 分支里也补了 401/403/404/5xx/超时/网络的兜底
（纵深防御，见 §6.2）。

捕获的异常类型：`BusinessException`、`MethodArgumentNotValidException`（取第一条字段错误）、
`HandlerMethodValidationException`、`HttpMessageNotReadableException`、`NoResourceFoundException`、
`DuplicateKeyException`、兜底 `Exception`。

其中 `DuplicateKeyException` 是**并发注册的兜底**：`existsByUsername` 检查与插入之间不是原子的，
两个并发请求可能都通过检查，此时由数据库 UNIQUE 约束拦下，在这里转成友好提示。

### 5.4 JWT 层 —— 为什么用拦截器而不是过滤器

`JwtAuthInterceptor implements HandlerInterceptor`。

**决定性理由：异常处理一致性。**

- `preHandle` 抛出的异常会进入 `DispatcherServlet#processHandlerException`，由**同一个**
  `@RestControllerAdvice` 解析，因此 `throw new BusinessException(-1, ...)` 能精确产出
  `{"code":-1, ...}`。
- 而 `OncePerRequestFilter` 在 DispatcherServlet **之外**运行，异常会走 Servlet 容器 →
  Boot 的 `BasicErrorController` → 完全不同的 JSON 结构（`{timestamp, status, error, path}`），
  前端拦截器**认不出来**。

次要理由：
- 过滤器要自己序列化 JSON，就要面对 Jackson 2/3 的陷阱（用错那个能编译通过但运行期行为错误）；
  拦截器完全不碰 `ObjectMapper`。
- `excludePathPatterns` 是声明式白名单，不用手写 `shouldNotFilter` 字符串匹配。

**`JwtUtil` 细节：**
- `@PostConstruct` 里 `Keys.hmacShaKeyFor(secret.getBytes(UTF_8))`。密钥不足 32 字节时这里抛
  `WeakKeyException` —— **启动即失败，好过运行期静默降级成不安全的签名**。
- 用户 id 放在 `sub` 里以**字符串**承载，解析端用 `Long.valueOf` 还原。
  **不用** `claims.get("userId", Long.class)`——那依赖 jjwt 在 JSON `Integer`/`Long` 之间的数值
  强制转换行为。

**`UserContext` + `ThreadLocal`：**
- `JwtAuthInterceptor.afterCompletion` **必须** `UserContext.clear()`。
  Tomcat 会复用线程，不清理会把一个用户的身份串到**下一个用户的请求**上。这是严重且难复现的安全 bug。

**白名单是「全量减放行项」，不是黑名单：**

```java
registry.addInterceptor(jwtAuthInterceptor)
        .addPathPatterns("/**")
        .excludePathPatterns("/user/login", "/user/register", "/error",
                             "/favicon.ico", "/assets/**", "/static/**", "/index.html", "/");
```

以后新增的接口**默认就是受保护的**。请不要把它改成「只拦截某几个路径」的形式。

> 注意 `excludePathPatterns` 里的路径是 **context-path 相对**的：配置了
> `server.servlet.context-path=/api` 之后要写 `/user/login`，不是 `/api/user/login`。

### 5.5 注册流程

`UserService.register`，`@Transactional(rollbackFor = Exception.class)`：

1. 校验 `password` 与 `confirmPassword` 相等
   （服务层普通判等，**不用**类级 `@AssertTrue` 跨字段校验——那会引入合成属性并牵扯序列化配置，
   收益为零风险不小）
2. `existsByUsername` / `existsByEmail` 查重
3. 先插 `sys_users`：`setStatus(2)`、`setIsDeleted(0)`；`lockedUntil` / `createdAt` / `updatedAt`
   一律不写，交给数据库。`save()` 拿回自增主键
4. 用**同一个 id** 插 `sys_user_auths`：`passwordHash = passwordEncoder.encode(password)`、
   `salt = "bcrypt$embedded"`

#### 🔴 这里踩过一个坑：`save()` 变成了 UPDATE，静默丢数据

**症状：** 注册接口返回成功、`sys_users` 里有行，但 `sys_user_auths` **一行都没有**，
导致该账号永远登录失败；重复注册同一用户名也不会被拦下。

**根因：** Spring Data JDBC 的 `save()` 依据 `isNew()` 决定发 INSERT 还是 UPDATE，而**默认的
`isNew()` 判定是「id 是否为 null」**。为了让两表 id 一致，代码里预先调用了 `auth.setId(userId)`，
于是 `save()` 判定这是「已存在的实体」，发出了一条 **UPDATE**：

```sql
UPDATE sys_user_auths SET ... WHERE id = 3   -- 表里根本没有 id=3，影响 0 行
```

UPDATE 影响 0 行**不抛异常**，事务照常提交 → 孤儿行诞生。这是个"成功路径上的静默失败"。

**修复：** 改用 `JdbcAggregateTemplate.insert(auth)`，它**强制**走 INSERT，不看 `isNew()`：

```java
auth.setId(userId);                          // 两表 id 必须一致
jdbcAggregateTemplate.insert(auth);          // 不能用 save()
```

（另一种等价方案是让 `SysUserAuths` 实现 `Persistable<Long>` 并覆写 `isNew()`，但改动面更大。）

**教训：** 只要手动设置了实体的 `@Id`，`save()` 就不再可靠。这种情况下一律用 `insert()`。

### 5.6 登录流程

`UserService.login`，`@Transactional(rollbackFor = Exception.class)`：

1. **用户名或邮箱均可登录**：`findByUsername(account).or(() -> findByEmail(account))`
   （前端表单项的 label 就是「用户名或邮箱」）
2. **先校验密码**，密码错就说「用户名或密码错误」
3. 再查 `sys_users` 校验 `is_deleted == 1`（拒绝）与 `locked_until`（在未来则拒绝）
4. 更新 `last_login_at`
5. 签发 JWT，返回 `LoginResponse(token, UserInfo)`

> **这个顺序是有意为之。** 先验密码、再查状态。反过来的话，攻击者不用知道密码，就能通过
> 「账号被锁定」这类提示确认某个账号**是否存在**。先验密码使得所有密码错误的路径都返回同一句话，
> 账号状态信息只暴露给已经证明拥有该账号的人。

### 5.7 `UserInfo` 绝不含敏感字段

`UserInfo` 是 `record(Long userId, String username, String email, Integer status, String statusText)`。

**绝不包含 `passwordHash` 或 `salt`。** 新增字段时请守住这条。

### 5.8 注册邮箱验证码

**需求：** 用户点「发送验证码」→ 60 秒倒计时（期间不能重发）→ 验证码 5 分钟有效 →
**5 分钟内重发则旧码立即作废**。

#### 5.8.1 为什么用 Redis 而不是 MySQL

「5 分钟过期」和「重发作废旧码」这两个需求，Redis 都**免费**给了：

| 需求 | Redis 的做法 |
|---|---|
| 5 分钟有效 | `SET key value EX 300`，到点自动消失，不需要任何清理任务 |
| 重发作废旧码 | 新码**直接覆盖同一个 key**，旧值就没了，**零额外代码** |

用 MySQL 的话，两件事都要自己写：加 `expires_at` 列 + 查询时判过期、重发时手动
`UPDATE ... SET code = ?`，还要一个清理历史行的定时任务。所以这里选 Redis 不是为了
「缓存快」，是因为 TTL 与覆盖写恰好就是需求本身。

#### 5.8.2 键设计

```
mha:emailcode:register:<email>    验证码明文     TTL = mha.email-code.expire-seconds（300s）
mha:emailcode:cooldown:<email>    冷却标记 "1"   TTL = mha.email-code.cooldown-seconds（60s）
mha:emailcode:fail:<email>        失败计数       TTL = 300s
```

键名里带 `register`：将来加「找回密码」时换成 `mha:emailcode:resetpwd:<email>` 即可，
同一套 `EmailCodeService` 可复用，不用改键结构。

#### 5.8.3 `EmailCodeService.send(email)`

顺序**很重要**：

1. **先抢冷却位**：`setIfAbsent(cooldownKey, "1", 60s)`。
   用 `setIfAbsent`（`SET NX EX`）而不是「先 `get` 判存在、再 `set`」——
   后者是 check-then-set，两个并发请求会同时通过检查，各发一封邮件。`SET NX` 是原子的。
2. 抢到就**覆盖写验证码键**（这一步就是「旧码作废」，不需要额外逻辑）。
3. 删掉失败计数（重新发码应该给足 5 次机会）。
4. 发邮件。**发送抛异常时删掉冷却键**——否则邮件没发出去，用户却被锁 60 秒，
   只能干等一个空倒计时。
5. 返回 `SendCodeResponse(expireSeconds, cooldownSeconds)`，前端用这两个数，不写死。

冷却被抢到时抛：`发送过于频繁，请 {剩余秒} 秒后重试`（剩余秒由 `getExpire()` 得到）。
**错误里带秒数是刻意的**：前端倒计时是纯体验，刷新页面就没了，而服务端冷却还在。
带上秒数前端才能把倒计时续上（见 §6.7），用户不会撞上一个没有倒计时的「发送过于频繁」。

#### 5.8.4 `verifyAndConsume(email, inputCode)`

| 情况 | 行为 |
|---|---|
| key 不存在（过期 / 从没发过 / 已消费） | 抛「验证码已过期，请重新获取」 |
| 不匹配 | 失败计数 +1；第 1 次失败时**才**给计数键设 TTL（避免每次失败都续期造成永久键） |
| 失败达到 `max-attempts`(5) | **删掉验证码键与计数键**，抛「验证码错误次数过多，请重新获取」 |
| 匹配 | `DELETE` 验证码键 + 计数键（**一次性使用**） |

码用 `SecureRandom` 生成、`String.format("%06d", ...)` 补零成 6 位。

#### 5.8.5 四个需要定死的设计点

1. **60 秒冷却必须服务端强制。** 只靠前端倒计时的话，刷新页面或直接 curl 就绕过了。
   **前端倒计时是体验，Redis 的 cooldown 键才是规则。**

2. **失败次数限制（5 次）是必须的。** 6 位数字码只有 10^6 种，5 分钟窗口内不限次数
   是可以爆破的。超过就作废验证码，强制重新获取。

3. **校验顺序：先查重（用户名/邮箱）再验码。** 反过来的话，「用户名已被注册」会白白
   烧掉一个验证码，用户得等满 60 秒冷却才能重新获取——一个纯属浪费的等待。
   把验码放在**最后**，失败路径不消耗码。这不引入新的信息泄露：接口本来就会返回
   「用户名已被注册」。

4. **验证码明文存 Redis，不做哈希。** 6 位码用 SHA-256 等于没哈希（离线爆破 10^6 次
   是瞬间的事），BCrypt 每次校验 ~100ms 且要为此多存一份盐。**真正的防线是
   「短 TTL + 失败次数限制」，不是存储形态。** 将来若需要收紧，改的是这两处，不是哈希。

#### 5.8.6 「消费」与数据库事务的关系（一个刻意的取舍）

`verifyAndConsume` 里删 Redis 键的动作**不在** `UserService.register` 的数据库事务内。
所以存在这个窗口：验码通过 → 插库失败回滚 → **验证码已经被消耗掉了**，用户需要重新获取。

反过来做（先插库、事务提交后再删码）会出现更糟的问题：**响应丢了但码还在**，
形成一个可重放窗口。两害相权取其轻，选了前者。这段取舍在 `UserService.register`
的注释里也写了一遍，避免维护时被「顺手修一下」。

#### 5.8.7 邮件双模式

```
mail/MailDelivery.java          接口：void send(String to, String subject, String text)
mail/SmtpMailDelivery.java      用 JavaMailSender + SimpleMailMessage
mail/LoggingMailDelivery.java   WARN 级别把验证码打在后端日志里
config/MailConfig.java          选哪一个
```

`MailConfig` **故意用一个 `@Bean` 方法里写 `if`**，而不是 `@ConditionalOnMissingBean`：

- `@ConditionalOnMissingBean` 在用户自己的 `@Configuration` 里**执行顺序没有保证**，
  两个 bean 条件互相看不见对方时会两个都创建或都不创建；
- 想用两个 `@ConditionalOnProperty` 表达「有 host / 没有 host」也不行——
  `matchIfMissing=true` 在属性**存在**时同样匹配，两边会同时成立。

判断依据是 `spring.mail.host` 是否非空**且** `JavaMailSender` bean 是否存在
（后者本身带 `@ConditionalOnProperty("spring.mail.host")`，没配 host 时根本不会被创建）。
走日志分支时启动会打一行：
`未配置 spring.mail.host —— 邮件不会真实投递，验证码将输出到本日志中`。

#### 5.8.8 接口白名单（漏了会被拦截器挡掉）

`/user/email-code` **必须**加进 `WebMvcConfig` 的 `excludePathPatterns`——
这个接口在登录**之前**就要用，不加的话会被 `JwtAuthInterceptor` 直接拒掉。

另外注意路径是 **context-path 相对**的：配了 `server.servlet.context-path=/api` 之后
写 `/user/email-code`，不是 `/api/user/email-code`。

## 6. 前端实现

### 6.1 Vite 代理

`vite.config.js`：`/api` → `http://localhost:8080`，**不写 `rewrite`**。

后端有 `server.servlet.context-path=/api`，两边都保留 `/api` 前缀。
**前缀只能由其中一方负责，同时做会变成 `/api/api/...`。**

### 6.2 `utils/request.js` —— 修掉的 4 个 bug

| # | 原问题 | 后果 | 修复 |
|---|---|---|---|
| a | `code === -1` 分支既不 `return` 也不 `reject` | promise resolve 成 `undefined`，调用方读 `res.data.token` 抛 **TypeError**，把「登录过期」的真实原因掩盖掉了 | `return Promise.reject(new Error(msg))` |
| b | 判断登录页时检查请求 url 是否含 `/auth/login`，而真实路径是 `/user/login` | 判断**永远不命中** | 改为判断浏览器当前在哪：`window.location.pathname.startsWith('/auth/')` |
| c | 非 -1 的错误分支 `Promise.reject(...)` 前没有 `return` | reject 被丢弃，调用方的 `catch` 永远不触发 | 加 `return` |
| d | axios error 分支直接透传，没有任何状态码处理 | 超时/断网/500 都只给一个笼统提示 | 补 401/403/404/5xx/超时/网络分支 |

另外新增：
- `redirecting` 标志位——并发请求同时失败时只跳转一次。
- 跳转用 `window.location.replace` 而非 `href`——不在历史栈留下受保护页面，
  否则退出/过期后按浏览器「后退」还能回到那个页面。
- 跳转时带上 `?redirect=<当前地址>`，登录后能回到原目标页。

### 6.3 `stores/user.js`

Pinia，**setup 风格**（对齐既有的 `stores/admin.js`）。

- `token` / `userInfo` 用 `ref` 从 localStorage 回填
- `isLoggedIn` / `username` / `isAdmin` 用 `computed`
- 动作：`login` / `register` / `logout` / `setAuth` / `clearAuth`
- localStorage 的 JSON 用 `safeParse` 容错——手工改过或旧版本残留的脏数据不能让整个应用起不来
- **store 不调 `ElMessage`**：响应拦截器已经提示过了，这里只 rethrow 让调用方中断流程

### 6.4 路由守卫

`router/index.js`：

- `/back` 加 `meta: { requiresAuth: true }`，`/auth` 加 `meta: { guestOnly: true }`
  —— 标在**父级**即可，Vue Router 4 会把匹配链上的 meta 合并进 `to.meta`，子路由自动继承
- `router.beforeEach`：未登录访问 `requiresAuth` → 跳 `/auth/login?redirect=<目标>`；
  已登录访问 `guestOnly` → 跳 `/back/dashboard`

两个细节：
- `/back` 本身没有子路由视图，直接落到它只会渲染出空布局，因此守卫把它归一化成 `/back/dashboard`
- 守卫内调 `useUserStore()` 是安全的：`main.js` 里 `app.use(pinia)` 在 `app.use(router)` **之前**，
  且守卫只在 mount 之后运行。**改动 `main.js` 时请保持这个顺序。**

### 6.5 `Navbar.vue` 退出登录

- 原来 `const userInfo = JSON.parse(localStorage...)` 只在 setup 时求值一次，**非响应式**，
  登录/退出后不会更新 → 改为 `computed(() => userStore.userInfo)`
- `handleCommand` 实现真正的退出：`ElMessageBox.confirm` 二次确认 → `userStore.logout()` →
  `router.replace('/auth/login')`（`replace` 而非 `push`，理由同 §6.2）
- 用户点「取消」时什么都不做，保持登录态
- `ElMessage` / `ElMessageBox` **必须显式 import**——`main.js` 里全局注册的只有 Element Plus 的
  **组件**，不含这些命令式函数

### 6.6 `login.vue` / `register.vue`

两个改动：

1. **`formEl.validate()` 改用纯 promise 形式。** 原来是 `await formEl.validate(callback)`——
   回调与 await 混用会让 `await` 拿到一个几乎立刻 resolve 的 `undefined`，
   **校验不通过时后面的登录/注册逻辑照样会执行**。
2. **加 try/catch。** 拦截器修好后失败会 reject，而两个视图原来都没有 catch，
   会变成未处理的 promise rejection。

`login.vue` 额外做了：登录成功后跳 `route.query.redirect`，但**只接受站内绝对路径**
（`/^\/(?!\/)/`）——该参数来自 URL query 是用户可控值，`//evil.com` 这种协议相对地址
会被浏览器当作外部站点，必须挡掉。

`register.vue`：payload 为 `{email, code, username, password, confirmPassword}`，
后端 `RegisterRequest` 显式声明并校验 `confirmPassword` 与 `code`，不依赖未知字段忽略策略。
（`code` 是本期新增，见 §6.7。）

### 6.7 `register.vue` 的「发送验证码」按钮与倒计时

`src/api/admin.js` 新增：

```js
export function sendCode(data){
    return service.post('/user/email-code', data, { timeout: 15000 })
}
```

**为什么单独放宽超时：** `request.js` 的默认 `timeout` 是 5000ms，而 SMTP 发信经常
超过 5 秒。用默认值会出现最坏的情况——**邮件其实已经发出去了**，前端却报「请求超时」，
用户以为没发出去，反复重试。这个坑在接入真实 SMTP 之前就会暴露。

`register.vue` 的实现要点：

| 点 | 做法 | 为什么 |
|---|---|---|
| 按钮位置 | `el-input` 的 `#append` 插槽 | 与输入框连成一体，不用额外栅格 |
| 禁用 | `:disabled="countdown > 0 \|\| sending"` | `sending` 防连点；`countdown` 防重发 |
| 秒数来源 | `res.data.cooldownSeconds` | 用后端返回值，前端不写死 60，改配置不用动前端 |
| 卸载清理 | `onBeforeUnmount(stopTimer)` | 定时器在跑而组件已卸载，回调会去改一个不存在的组件的状态 |
| 发送前校验 | `ruleFormRef.value.validateField('email')` | **只校验邮箱一项**：整表校验会把「请输入用户名」等还没填的必填提示一起弹出来，干扰正在逐项填表的人 |
| 失败后 | 不进入倒计时 | 发信失败绝不能把用户锁在假倒计时里 |

**倒计时的续接**（对应 §5.8.3 错误里带秒数）：

```js
const remain = /(\d+)\s*秒/.exec(e?.message || '')
if (remain) startCountdown(Number(remain[1]))
```

典型场景是**倒计时期间刷新页面**：前端定时器没了，按钮回到可点状态，但服务端冷却还在。
这时点下去收到「发送过于频繁，请 42 秒后重试」，正则把 42 提出来接着倒计时，
用户就不会撞上一个没有倒计时、点一次错一次的按钮。

> 这里依赖 `request.js` 的约定，已核对过：**业务错误**（HTTP 200 + `code:500`）走的是
> `Promise.reject(new Error(msg))`，所以 `e.message` 就是服务端那句中文提示；
> 而**传输层错误**（超时/断网）reject 的是原始 axios error，`e.message` 是
> `timeout of 15000ms exceeded` 之类，正则匹配不到——此时**恰好不该**起倒计时，
> 因为服务端并没有在冷却。这个区分是巧合还是设计？是设计：见 §6.2 的响应拦截器分支。

> **倒计时是体验，不是防线。** 刷新页面丢掉倒计时**不会**绕过 60 秒限制——
> 服务端 Redis 的 cooldown 键仍然会拒绝，前端只是把剩余秒数接回来显示。

## 7. 冻结的接口契约

```
POST /api/user/email-code                              // 匿名可访问（在拦截器白名单里）
  req  {"email":"alice@example.com"}
  200  {"code":200,"msg":"验证码已发送","data":{"expireSeconds":300,"cooldownSeconds":60}}
  200  {"code":500,"msg":"该邮箱已被注册","data":null}
  200  {"code":500,"msg":"发送过于频繁，请 42 秒后重试","data":null}   // 带剩余秒数，前端据此续倒计时
  200  {"code":500,"msg":"邮箱格式不正确","data":null}
  200  {"code":500,"msg":"邮件发送失败，请稍后重试","data":null}

POST /api/user/register
  req  {"username":"alice","email":"alice@example.com","password":"123456",
        "confirmPassword":"123456","code":"287447"}
  200  {"code":200,"msg":"注册成功","data":{"userId":1}}
  200  {"code":500,"msg":"用户名已被注册","data":null}      // 注意：不消耗验证码
  200  {"code":500,"msg":"邮箱已被注册","data":null}        // 注意：不消耗验证码
  200  {"code":500,"msg":"两次输入的密码不一致","data":null}
  200  {"code":500,"msg":"邮箱格式不正确","data":null}
  200  {"code":500,"msg":"验证码不正确","data":null}
  200  {"code":500,"msg":"验证码已过期，请重新获取","data":null}
  200  {"code":500,"msg":"验证码错误次数过多，请重新获取","data":null}

POST /api/user/login
  req  {"username":"alice","password":"123456"}        // username 字段也接受邮箱
  200  {"code":200,"msg":"登录成功","data":{
         "token":"eyJ...",
         "userInfo":{"userId":1,"username":"alice","email":"alice@example.com",
                     "status":2,"statusText":"普通用户"}}}
  200  {"code":500,"msg":"用户名或密码错误","data":null}

GET /api/user/info                                      // 受保护
  无 token / 过期 / 签名错 → HTTP 200 + {"code":-1,"msg":"登录已过期，请重新登录","data":null}
  带 Bearer token         → HTTP 200 + {"code":200,"msg":"操作成功","data":{...userInfo...}}
```

前端依赖六个东西，均由上表锁定：`code:-1` 哨兵值、`data.token`、`data.userInfo.username`、
`/api` 前缀、`data.cooldownSeconds`、`data.expireSeconds`。
另外「发送过于频繁」的提示语**必须保留「X 秒」这个格式**——前端用 `/(\d+)\s*秒/`
从中取剩余秒数（§6.7），改文案时别把数字丢掉。

## 9. 已知约束与待办

### 9.1 当前设计的永久约束

- `salt` 占位列是既定约束（BCrypt 的盐已内嵌在哈希串里）。
- `sys_user_auths.id` 已作为外键关联 `sys_users.id`（§4.1）。注意这是**同一个主键兼任外键**的
  1:1 结构，不是独立自增 id + 关联列——从表 id 必须由主表回填。
  邮箱验证码也**没有新增任何 MySQL 表**——验证码全在 Redis（§5.8.1）。
- `sys_users.status` 的默认值已统一为 `2`（见 §4.2 坑 1），文档与线上表不再有偏差。

### 9.2 已知问题

- **`/back` 会渲染空布局**：`/back` 没有子路由视图，直接落到它只渲染出 `BackendLayout` 的空壳。
  登录页的「返回首页」链接正是指向 `/back`，所以**登录态下点它会白屏**。
  这是既有结构问题，本期未动路由结构；修法是加一条 `{ path: '', redirect: 'dashboard' }` 子路由。
- **token 无法主动失效**：无状态 JWT 的固有代价。退出登录只是前端清 localStorage，
  旧 token 在有效期内仍然可用。若需要真正的登出，得引入 Redis 黑名单。
- **`request.js` 的 `timeout` 是 5000ms**：对将来的 AI 对话类接口（流式/长耗时）太短，接入时需要调大。
  目前只有「发送验证码」在调用处单独放宽到 15000ms（§6.7），**不是**改全局默认值——
  改全局会让所有接口的超时都变长。
- **`sendCode` 放宽超时后，成功提示会在最长 15 秒后才出现**：SMTP 是真慢，
  超过 5 秒是常态。将来若觉得体感差，正确做法是把发信改成异步（先返回「已发送」，
  后台线程发信、失败再补偿），而不是把超时调回去。

### 9.3 安全注意

- `jwt.secret` 目前硬编码在 `application.properties` 里，**生产环境必须改为环境变量注入**
  （`jwt.secret=${JWT_SECRET}`）。
- `spring.ai.openai.api-key` 从环境变量 `API_KEY` 读取（兼容 `${OPENAI_API_KEY:not-configured}`），
  未配置时用占位值启动（Spring AI 的自动配置在启动时就必须能拿到凭证，否则应用起不来）。

邮箱验证码引入的新注意点：

- **验证码明文存 Redis。** 这是 §5.8.5 的设计取舍，不是疏忽：6 位码哈希等于没哈希。
  真正的防线是短 TTL + 5 次失败上限。**要收紧就收紧这两处。**
- **Redis 目前单点、无密码**，`spring.data.redis.host/port` 明文写在
  `application.properties` 里。生产必须加 `requirepass` 并把口令改成环境变量注入；
  否则任何能连到 6379 的人都能读走所有未过期验证码，或塞满内存。
- **防刷只到「每邮箱 60 秒一次」这一层，没有「每 IP 每日上限」。**
  这意味着有人可以拿这个接口定向轰炸某个邮箱（60 秒一封）。
  上线前应补 IP 维度限流——本项目里对应 §5.8.2 的 `mha:emailcode:*` 加一个 IP 键。
- **`POST /user/email-code` 是一个邮箱枚举面**：它会明确返回「该邮箱已被注册」。
  这是刻意的——注册页需要立刻告诉用户换个邮箱（对照 §5.6：登录接口反过来，
  绝不泄露账号是否存在）。如果将来觉得这个枚举风险不可接受，
  改法是统一回「验证码已发送」、把冲突推迟到提交注册时再报。
